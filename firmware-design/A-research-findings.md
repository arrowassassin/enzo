# Appendix A — Verified research findings (deep-research run, 2026-09-13)

Method: 5 search angles, 22 sources fetched, 84 claims extracted, 25 verified by 3-vote adversarial review (21 confirmed, 4 refuted), merged into the 10 findings below. Confidence and vote counts are from that run. Everything here is a snapshot as of September 2026; the ecosystem (CrossPoint releases, epdsi, esp-hal) moves quickly.

## Summary

The Xteink X3 is an ESP32-C3-class device (single-core RISC-V, ~400 KB SRAM of which only ~380 KB is usable, no PSRAM, 16 MB flash, microSD, Wi-Fi/BLE) whose sibling X4 uses an 800x480 SSD1677 panel; the X3 itself has a different 3.7-inch 528x792 panel whose controller is reported inconsistently across sources. The dominant community firmware, CrossPoint Reader (C++/PlatformIO, MIT, ~7.8k stars) and its forks (CrossInk, papyrix-reader), already prove the whole feature envelope on this hardware: on-device EPUB 2/3 with hyphenation/kerning/images, TXT/BMP/XTC, StarDict dictionaries, KOReader sync, and a full wireless-sideloading stack (web upload UI, WebSocket uploads, WebDAV, OPDS with saved servers, Calibre wireless, GitHub OTA) - all achieved by aggressively caching parsed chapters and metadata to SD. Two independent Rust projects (pulp-os with esp-hal 1.0 + embassy + a no_std smol-epub parser; TernOS with a desktop pre-rendered .trbk format) show both viable architectures for a Rust firmware: parse EPUB on-device with streaming HTML-strip and SD chapter cache and ~140-172 KB heap budget, or move parsing/layout to the desktop and stream pre-laid-out pages. The Rust ecosystem provides usable building blocks - fontdue (no_std, alloc-based TTF/OTF rasterizer, best used at build time to bake 1-bit bitmap fonts), epdsi (new no_std embedded-hal 1.0 driver framework covering SSD1677/UC8253 with paged rendering that avoids full framebuffers, hardware-verified on ESP32-C3 with esp-hal), and epd-waveshare (mature but limited to Waveshare panel modules) - while the EPub-InkPlate project on a PSRAM-equipped ESP32 documents the practical hazards: streaming image decoders are mandatory, fonts must be subsetted, and Wi-Fi buffers alone can exhaust internal RAM. Realistically, native on-device support should be scoped to EPUB, TXT, and simple images, with PDF/MOBI/DjVu/DOCX and other heavy formats handled by desktop pre-conversion; the display strategy should follow the proven pattern of DU/partial refresh (~400 ms) for page turns with a periodic full refresh (every ~10 turns) to limit ghosting, plus auto-sleep after inactivity.

## Findings

### F1. The Xteink X3 and X4 are ESP32-C3-based e-readers (single-core RISC-V RV32IMC @160 MHz, 16 MB flash, no PSRAM) with only ~380 KB of usable RAM, a constraint every existing firmware explicitly designs around; the newer X4 Pro and other S3-class devices (Seeed reTerminal Sticky, M5PaperMono) have ESP32-S3 with 8 MB PSRAM and are a different hardware class.

- **Confidence:** high (vote 3-0 (claims 0, 1, 3, 4 merged))
- **Evidence:** CrossPoint README: 'Now running on: ESP32C3-based Xteink X4 and X3. ESP32S3-based Xteink X4Pro, Seeed reTerminal Sticky, M5PaperMono' and 'The ESP32-C3 only has ~380KB of usable RAM, so we have to be careful' (given as the rationale for SD-card chapter/metadata caching). platformio.ini uses esp32-c3-devkitm-1 for the default env and esp32-s3-devkitc1-n16r8 (16MB flash / 8MB PSRAM) for x4pro/sticky. Espressif datasheet: 400 KB SRAM with 16 KB reserved for cache. papyrix-reader device-specifications lists X3/X4 as ESP32-C3 16 MB flash and X4 Pro as ESP32-S3 with 8 MB octal PSRAM. Some AliExpress units ship USB-flash-locked and need the Xteink Unlocker tool.
- **Sources:** <https://github.com/crosspoint-reader/crosspoint-reader>, <https://github.com/tstapler/CrossInk>, <https://github.com/hansmrtn/pulp-os>, <https://github.com/bigbag/papyrix-reader/blob/main/docs/device-specifications.md>

### F2. Xteink X4 hardware (sibling of the X3): 800x480 monochrome e-paper (GDEQ0426T82) driven by an SSD1677 controller over DMA-backed SPI shared with the SD card (SPI2), ~400 KB DRAM with roughly 172 KB heap actually usable under pulp-os's Rust stack, ~650 mAh battery, no touch. The X3 differs: a 3.7-inch ~250 PPI 528x792 panel, and its controller is reported as UC8253/UC8279 by papyrix-reader docs but SSD1677 by other community notes.

- **Confidence:** high (vote 3-0 (claim 7))
- **Evidence:** pulp-os README: 'ESP32-C3, single-core RISC-V RV32IMC, 160 MHz ... 800x480 SSD1677 mono e-paper, DMA-backed SPI, portrait ... 400 KB DRAM; ~172 KB heap (108 KB main + 64 KB reclaimed)'; EPD and SD share SPI2. Adafruit: X4 has ESP32-C3, no PSRAM, 400 KB SRAM, 16 MB flash. TernOS README: 'XTEink X4 (ESP-C3 RiscV core, ~512kb RAM, 480x800 epd, no touch)'. The 172 KB heap figure is a firmware-stack measurement, not a hardware constant; heap under ESP-IDF with Wi-Fi/BLE is typically ~300 KB or less. X3 panel/controller identity is inconsistent across sources (UC8253/UC8279d vs SSD1677) and must be confirmed by teardown.
- **Sources:** <https://github.com/hansmrtn/pulp-os>, <https://learn.adafruit.com/circuitpython-on-the-xteink-x4-ereader>, <https://github.com/bigbag/papyrix-reader/blob/main/docs/device-specifications.md>, <https://github.com/azw413/TernOS>

### F3. CrossPoint Reader (and forks CrossInk, papyrix-reader) is the reference open-source firmware for the X3/X4: C++/Arduino via pioarduino/PlatformIO (pio run --target upload), MIT, ~7.8k stars, actively released (v1.6.0, Sept 2026). It natively parses only .epub, .xtc/.xtch, .txt and .bmp; EPUB 2/3 rendering includes embedded-style option, images (PNG/JPEG converted to BMP), hyphenation, kerning, adaptive tables, CJK ruby, chapter navigation, footnotes, bookmarks, go-to-percent, auto page turn, orientation control, focus reading, StarDict dictionary lookup (with .syn synonyms and HTML definitions rendered via the EPUB engine) and KOReader progress sync. FB2/Markdown exist only in forks; no PDF/MOBI/CBZ parser exists in mainline. No Rust code exists in this lineage.

- **Confidence:** high (vote 3-0 (claims 2, 4, 5 merged))
- **Evidence:** README: 'native handling for `.epub`, `.xtc/.xtch`, `.txt`, and `.bmp`' and 'EPUB 2/3 rendering with embedded-style option, image handling, hyphenation, kerning, chapter navigation, footnotes, bookmarks, go-to-percent, auto page turn, orientation control, focus reading, KOReader progress sync'. lib/ tree contains only Epub, Txt, Xtc parsers plus OpdsParser, PngToBmpConverter, JpegToBmpConverter, ZipFile, miniz/uzlib/expat. Community-forks section attributes FB2/MD to papyrix-reader and Witch(hunt) Reader; CrossInk adds only typography (Bionic Reading, guide dots, paragraph indents, extra fonts). Cargo.toml returns 404 in both CrossInk repos; platformio.ini declares framework = arduino, check_tool = cppcheck.
- **Sources:** <https://github.com/crosspoint-reader/crosspoint-reader>, <https://github.com/tstapler/CrossInk>, <https://github.com/uxjulia/CrossInk>

### F4. Wireless sideloading on the ESP32-C3 X3/X4 is fully demonstrated by CrossPoint/CrossInk: a file-transfer web UI with WebSocket fast uploads, a WebDAV handler, an OPDS catalog browser (up to 8 saved servers, search, pagination, direct download), a Calibre wireless-device connect flow, a web settings UI/API, KOReader progress sync, and OTA update checks/installs from GitHub releases (the only update path for USB-locked units).

- **Confidence:** high (vote 3-0 (claim 6))
- **Evidence:** README lists 'File transfer web UI', 'WebSocket fast uploads', 'WebDAV handler', 'OPDS browser with saved servers (up to 8), search, pagination, and direct download', 'Calibre wireless connect flow', 'OTA update checks and installs from GitHub releases'. Implementation confirmed in source: src/network/WebDAVHandler.cpp, src/OpdsServerStore.cpp, lib/OpdsParser/OpdsParser.cpp, src/activities/network/CalibreConnectActivity.cpp, docs/webserver-endpoints.md. Third-party firmware guides (PocketInk) corroborate. Functionality originates upstream in CrossPoint; CrossInk inherits it. A narrower phrasing of this claim was refuted 1-2 only because it omitted OPDS/Calibre/WebSocket, not because the features are absent.
- **Sources:** <https://github.com/tstapler/CrossInk>, <https://github.com/crosspoint-reader/crosspoint-reader>, <https://github.com/crosspoint-reader/crosspoint-reader/blob/develop/docs/webserver-endpoints.md>

### F5. Architecture option A - on-device EPUB parsing in Rust is feasible on the ESP32-C3 (pulp-os, MIT, esp-hal 1.0.0 + embassy, targeting the X4): a ZIP/OPF/HTML-strip pipeline (no_std smol-epub, designed for ~140 KB heap, measured peaks ~51 KB chapter strip, ~90 KB PNG streaming, ~30 KB JPEG) with chapter cache on SD, proportional fonts with bold/italic/heading style markers (not full CSS layout), inline PNG/JPEG rendered as 1-bit Floyd-Steinberg dithered images, TOC from NCX or inline, and a lazily page-indexed TXT reader with read-ahead prefetch.

- **Confidence:** high (vote 3-0 (claim 8))
- **Evidence:** pulp-os README: 'epub reader ZIP/OPF/HTML-strip pipeline, chapter cache on SD ... inline PNG/JPEG (1-bit Floyd-Steinberg dithered) ... TOC browser (NCX or inline); txt reader lazy page-indexed, read-ahead prefetch'. Cargo.toml: esp-hal 1.0.0 feature esp32c3, embassy, smol-epub path dep, fontdue build-dep; src/apps/reader/epub_pipeline.rs and images.rs exist. smol-epub README: 'Minimal no_std EPUB parser ... Designed for devices with as little as ~140 KB of heap'. Author describes the project on the Xteink forum as personal and 'very much in development' with no install guide. A stronger claim that pulp-os is a 'working' firmware on esp-rtos with no dynamic dispatch flashable via espflash was refuted 0-3, so treat it as a proof-of-concept, not a shippable base.
- **Sources:** <https://github.com/hansmrtn/pulp-os>, <https://github.com/hansmrtn/smol-epub>

### F6. Architecture option B - desktop pre-rendering: TernOS (Rust, targeting the X4 and M5Paper) does not parse EPUB on-device; a tern-book desktop tool converts EPUB into a compact pre-rendered .trbk format (page LUT, draw ops, bitmap glyph table) that the device streams page-by-page, explicitly to keep firmware fast and low-memory.

- **Confidence:** high (vote 3-0 (claim 10))
- **Evidence:** README: 'TernReader converts epub books into a compact binary format (trbk) so that rendering and reading will be fast and small on device'; 'TRBK is a pre-rendered book format generated on desktop. It keeps the firmware fast and low-memory by moving EPUB parsing/layout off-device'; spec: 'The device streams pages from the LUT and renders ops directly'. Source tree contains core/src/app/book_reader.rs and x4/src/eink_display.rs. A separate claim about TernOS's exact no_std/esp-hal stack was refuted 0-3, so only the format strategy, not the toolchain details, should be cited. This mirrors CrossPoint's XTC/XTCH pre-rendered format and the EPUB Optimizer workflow.
- **Sources:** <https://github.com/azw413/TernOS>

### F7. Proven e-ink refresh and power UX patterns on this hardware: page turns use a fast/partial DU waveform (~400 ms on SSD1677) with a periodic full refresh (TernOS: every 10 page turns) to limit ghosting; pulp-os uses a 3-phase partial refresh (write BW RAM, kick DU waveform, collect button input during the ~400 ms refresh, then sync RED RAM) so input is never lost during refresh; auto-sleep after 5 minutes idle with the power button able to force sleep.

- **Confidence:** high (vote 3-0 (claims 9, 11 merged))
- **Evidence:** pulp-os README/scheduler.rs: '3-phase partial refresh. write BW RAM, kick DU waveform, collect input during ~400 ms refresh, then sync RED RAM'; app.rs 'deferred input during EPD refresh'; skips phase 3 when content changed mid-DU. TernOS README: 'Page turns use fast refresh with periodic full refresh to limit ghosting', 'Auto-sleep after inactivity (5 minutes)'; book_reader.rs const BOOK_FULL_REFRESH_EVERY = 10; system.rs idle_timeout_ms = 300_000. The ~400 ms figure is an author comment, not a published measurement.
- **Sources:** <https://github.com/hansmrtn/pulp-os>, <https://github.com/azw413/TernOS>

### F8. Font strategy: fontdue (v0.9.4, Jul 2026) is a pure-Rust no_std TrueType/OpenType rasterizer that compiles for riscv32imc via a scalar fallback, but it is allocation-heavy (requires the alloc crate, fully parses fonts into HashMaps/Vecs on load), so on a PSRAM-less ESP32-C3 the proven pattern (pulp-os) is to rasterize TTFs in build.rs into 1-bit bitmap glyphs at five sizes (16-35 px) and three styles (regular/bold/italic) rather than rasterize at runtime; EPub-InkPlate's runtime FreeType approach on an 8 MB-PSRAM ESP32 still required subsetting fonts to Latin-1 plus targeted extensions and enforcing 400 KB/800 KB font budgets.

- **Confidence:** high (vote 3-0 (claims 9, 17, 19, 20 merged))
- **Evidence:** fontdue README: 'no_std ... pure Rust, TrueType (.ttf/.ttc) & OpenType (.otf) font rasterizer' and 'This library does make allocations and depends on the alloc crate'; src/lib.rs has extern crate alloc and cfg-gated SIMD with scalar fallback; deps only ttf-parser and hashbrown. pulp-os build.rs: 'rasterise to 1-bit bitmaps, emit font_data.rs ... five size tiers', fontdue::Font::from_bytes for regular/bold/italic. EPub-InkPlate README: 'FreeType upgraded to v2.14.3', 'natively support kerning, alongside a lightweight custom algorithm for standard ligatures', 'All fonts have been subsetted to Latin-1 plus some usual characters', hyphenation limited because 'The memory limitations of the ESP32 do not allow for more languages'. No published example of fontdue running at runtime on an ESP32 was found.
- **Sources:** <https://github.com/mooman219/fontdue>, <https://github.com/hansmrtn/pulp-os>, <https://github.com/turgu1/EPub-InkPlate>

### F9. Rust e-paper driver options: epdsi (v0.3.1, Sept 2026) is a no_std embedded-hal 1.0 blocking/async driver framework covering SSD1680/SSD1681/SSD1677, UC8253, JD79661, ED2208 and Pervasive Displays COG controllers, implementing embedded-graphics DrawTarget/Dimensions (default 'graphics' feature) and GxEPD2-style closure-based paged rendering with small stack buffers so no full-frame framebuffer (~48 KB for 800x480 mono) is needed; it is hardware-verified in blocking mode on a Seeed XIAO ESP32-C3 with esp-hal and async on ESP32-S3 with Embassy. epd-waveshare (v0.6.0, Oct 2024, embedded-hal 1.0, optional embedded-graphics-core 0.4) is mature but only exposes Waveshare panel-model modules (epd1in02 ... epd12in48b_v2), with no 6-inch reader panel, no IT8951, and modules named by panel not controller.

- **Confidence:** medium (vote 3-0 (claims 12, 13, 14, 15 merged))
- **Evidence:** epdsi README: 'no_std embedded-hal 1.0 compatible Rust driver framework, blocking or async ... SSD1680, SSD1681, SSD1677, UC8253, JD79661, ED2208, Pervasive Displays COG'; 'Low-RAM Paged Rendering: Built-in support for GxEPD2-style closure-based paged graphics rendering using tiny stack buffers'; lib.rs: 'render_paged sweeps the panel one horizontal band at a time ... RAM use depends on chosen page height, not panel size'; verification matrix lists SSD1677 and UC8253 as 'Verified blocking: RP2350, RP2040, ESP32-C3'. Cargo.toml default = [blocking, graphics]. epd-waveshare Cargo.toml: version 0.6.0, embedded-hal 1.0.0, embedded-graphics-core 0.4 optional behind graphics feature; src/ lists only panel modules. Medium confidence because epdsi is ~3 weeks old, single-author, ~275 downloads, self-reported verification, breaking API changes across 0.1-0.3, no ESP32-C3 async verification; a claim that its SSD1677 partial refresh measured ~4.1 s on RP2350 was refuted 0-3, so partial-refresh timing on epdsi is unverified. Notably epdsi covers both controllers reported for the X3 (SSD1677 and UC8253).
- **Sources:** <https://docs.rs/epdsi/latest/epdsi/>, <https://github.com/melastmohican/epdsi>, <https://github.com/rust-embedded-community/epd-waveshare>, <https://github.com/melastmohican/xiao-esp32c3-blinky>

### F10. Lessons from the mature C++ EPub-InkPlate reader (ESP32 @240 MHz with 4 MB+4 MB PSRAM, ESP-IDF, v3.0.1 Aug 2026) that bound what is realistic on a PSRAM-less ESP32-C3: PSRAM is mandatory there even for Wi-Fi/LWIP buffers because internal RAM is insufficient; STB image decoding had to be replaced by streaming decoders (PNGLE modified for grayscale, TJPGD for JPEG, MINIZ for deflate) to bound memory; per-book page-location (.locs) and TOC caches are stored on SD; and initial indexing costs 5-10 s per ebook, so library scans must be cached.

- **Confidence:** high (vote 3-0 (claims 16, 18 merged))
- **Evidence:** README: 'The PSRAM is an extension to the ESP32 memory that offers 4MB+4MB of additional RAM ... The WiFi implementation use a large portion of memory. There is not enough main memory available for the buffer required, so it must be allocated from the PSRAM'; 'The processor must be run at 240MHz'; stb_image.h 'Requires a lot of memory space depending on the ePub stored image resolution. Changed to use PNGLE and TJPGD combined with my own image classes to stream the image'; 'all books .locs and .toc files needs to be refreshed'; 'The refresh process takes some time (between 5 and 10 seconds per ebook)'. Implication: the EPub-InkPlate design (runtime FreeType, full CSS-ish layout) does not transfer to the X3 without the pre-rendering or streaming-strip simplifications used by pulp-os/TernOS/CrossPoint.
- **Sources:** <https://github.com/turgu1/EPub-InkPlate>

## Caveats from the run

(1) The X3's exact panel controller is unresolved: papyrix-reader documentation lists UC8253/UC8279d while other community notes say SSD1677 (the X4's controller); both are covered by epdsi, but the driver choice, waveform timings, and partial-refresh behavior must be confirmed against the actual X3 board. (2) All Rust evidence comes from the X4 (pulp-os, TernOS), not the X3; resolutions (800x480 vs 528x792) and pin maps differ, so nothing is a drop-in port. (3) The refuted claims show that details about pulp-os and TernOS toolchains (esp-rtos, espflash, no dynamic dispatch, exact RAM) were overstated by the original extraction; only their architecture patterns and README-stated features should be relied on, and pulp-os's author calls it in-development with no install guide. (4) epdsi is a very new single-author crate with self-reported verification and unstable API; its partial-refresh performance is unverified. (5) Usable heap figures (~380 KB, ~172 KB, ~140 KB) come from different stacks and are not comparable; a Rust firmware with Wi-Fi/BLE enabled must re-measure. (6) The research angles on non-EPUB formats (MOBI/AZW3, PDF, DjVu, CBZ, FB2, DOCX, RTF), Rust crates for them, BLE transfer from phones, captive portals, and the broader e-reader UX/games survey produced no surviving claims; those sections of the report rest on inference from the confirmed constraints (no native PDF/MOBI in any ESP32-C3 firmware found) rather than direct evidence. (7) No claims about the X3 stock firmware, bootloader, battery, or teardown survived beyond the USB-flash-lock/Unlocker note. (8) Sources are current as of Sept 2026 but the ecosystem (CrossPoint releases, epdsi, esp-hal) moves quickly.

## Open questions the run could not close

- Which e-paper controller and panel part number does the Xteink X3 actually use (UC8253/UC8279 vs SSD1677), what are its pinout, SPI sharing with SD, and supported waveforms (DU, GC, any 4-gray mode), and does epdsi drive it correctly?
- How much heap remains on the ESP32-C3 under a Rust stack (esp-hal/esp-radio or esp-idf-hal) with Wi-Fi plus a TLS HTTP client active, and does that leave enough for the ~50-90 KB peaks of streaming EPUB/image parsing, or must sideloading and reading be mutually exclusive modes?
- What do the X3 stock firmware and its companion app provide (formats, transfer protocol, OTA/bootloader, USB flash locking), and is there any risk of bricking or losing the stock bootloader when flashing custom Rust firmware via espflash?
- Which non-EPUB formats (MOBI/KF8, FB2, CBZ, Markdown, PDF) can be handled by a no_std Rust parser within a ~100 KB budget versus requiring a desktop converter, and are there existing Rust crates (e.g. for MOBI or DjVu) that build for riscv32imc at all?

## Claims that were refuted (do not rely on these)

- (1-2) CrossPoint's wireless sideloading consists of a WiFi file-transfer web UI, a WebDAV handler, a web settings UI/API, and OTA updates pulled from GitHub releases. — <https://github.com/crosspoint-reader/crosspoint-reader>
- (0-3) A working from-scratch no_std Rust e-reader firmware for this ESP32-C3 hardware exists (pulp-os, MIT) using the embassy async executor on esp-rtos, targeting riscv32imc-unknown-none-elf, with no framebuffer and no dynamic dispatch, and flashable via espflash. — <https://github.com/hansmrtn/pulp-os>
- (0-3) The Xteink X4 (sibling of the X3) runs an ESP32-C3 RISC-V SoC with roughly 512 KB RAM, a 480x800 e-paper display, and no touchscreen, and TernOS targets it with a no_std Rust firmware built on esp-hal. — <https://github.com/azw413/TernOS>
- (0-3) epdsi supports the SSD1677 controller driving the GDEQ0426T82 4.26-inch 800x480 monochrome panel with a differential Partial refresh mode, but the measured partial update on RP2350 was ~4.1 s rather than the ~500 ms the reference driver quotes. — <https://docs.rs/epdsi/latest/epdsi/>
