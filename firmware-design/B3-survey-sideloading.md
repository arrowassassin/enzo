# Appendix B3 — Wireless sideloading survey (agent report, 2026-09-13)

## 2. iPhone constraints and opportunities

- **Safari `<input type=file>`** opens the Files picker; an EPUB from Books can be exported via Share → *Save to Files* first (purchased Books titles cannot). [macobserver](https://www.macobserver.com/tips/how-to/how-to-transfer-files-from-books-app-to-files-app/), [softorino](https://softorino.com/blog/how-to-open-epub-on-iphone)
- **Web Share Target: not supported on iOS** (Safari/PWA cannot appear in the share sheet as a receiver, 2026). Web Share *out* works. [magicbell 2026](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide), [ojapp 2026](https://tips.ojapp.app/en/pwa-ios-2026-complete-guide/), [MDN share_target](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)
- **Files "Connect to Server" is SMB-only**; WebDAV needs a third-party File Provider (FileBrowser, Documents, WebDAV Navigator). So WebDAV on the device helps macOS Finder/Windows Explorer/Android file managers, not stock iOS Files. [Apple: transfer to server](https://support.apple.com/guide/iphone/transfer-files-iphone-a-storage-device-server-iphe9aff429a/ios), [stratospherix](https://www.stratospherix.com/articles/how-to-access-filebrowser-locations-from-files-app.php), [Apple community](https://discussions.apple.com/thread/8094559)
- **Bonjour/.local works on iOS**; Mobile Safari is exempt from the iOS 14 Local Network prompt, native apps must declare `NSLocalNetworkUsageDescription`. [WWDC20](https://developer.apple.com/videos/play/wwdc2020/10110/), [discuss-webrtc note on Safari exemption](https://groups.google.com/g/discuss-webrtc/c/CwXK55Y2sb8)
- **Captive portal**: iOS probes `http://captive.apple.com/hotspot-detect.html` expecting a "Success" page; ESP32 wildcard DNS (`dnsServer.start(53,"*",softAPIP)`) returning its own IP triggers the CNA sheet. Caveats: HTTPS probes can't be intercepted; the CNA mini-browser is stripped down (no inspector, restricted links) so file uploads inside it are unreliable — use it only to show a "Open in Safari" link/URL; iOS 26 reports of CNA failing mid-load with "network connection was lost". Android probes `connectivitycheck.gstatic.com/generate_204` (Samsung hard-codes DNS; workaround AP IP = 8.8.8.8). [espboards](https://www.espboards.dev/troubleshooting/issues/wifi/esp32-captive-portal-issues/), [foxblock/esp-captive-portal](https://github.com/foxblock/esp-captive-portal), [Apple forums iOS 26](https://developer.apple.com/forums/thread/805035), [CNA limitations](https://discussions.apple.com/thread/5258403)
- **Web Bluetooth: not in iOS Safari** (WebKit opposes generic peripheral APIs; only Bluefy/WebBLE browsers). A native app would be required for BLE. [caniuse](https://caniuse.com/web-bluetooth), [WebKit bug 101034](https://bugs.webkit.org/show_bug.cgi?id=101034)
- **BLE throughput**: ESP32↔ESP32 up to ~90 KB/s (1M PHY) / ~170 KB/s (2M); iPhone limits to 15 ms interval and ~5 packets/event, so realistic 30–80 KB/s well-tuned, ~60 KB/s via L2CAP CoC, and naive GATT writes seen at 5–7 KB/s. A 2 MB EPUB = 30 s–7 min. Wi-Fi is 20–50× faster. [ESP-FAQ](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/bt/ble.html), [Punch Through](https://punchthrough.com/maximizing-ble-throughput-on-ios-and-android/), [arduino-esp32 #8540](https://github.com/espressif/arduino-esp32/issues/8540), [esp32.com L2CAP](https://esp32.com/viewtopic.php?t=15033)
- **iOS Shortcuts as a no-app share target**: a Shortcut accepting Files from the share sheet + *Get Contents of URL* (POST, body = Form, file field) does multipart upload to `http://192.168.x.x/upload` or `http://reader.local/upload`; plain-HTTP local URLs work. This is the best "Send to reader" share-sheet story on iOS without an App Store app. [Apple Shortcuts guide](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios), [IndieWeb Shortcuts](https://indieweb.org/Shortcuts), [Automators talk](https://talk.automators.fm/t/send-post-request-with-get-contents-of-url/15943)
- **AirDrop**: Apple-proprietary, not implementable on ESP32.

## 3. Android

- **Web Share Target works in Chrome ≥76 for installed PWAs** (`share_target` with `enctype: multipart/form-data`, `params.files` accept list) — an installed PWA served by the reader can literally appear in the share sheet. [Chrome docs](https://developer.chrome.com/docs/capabilities/web-apis/web-share-target), [web.dev](https://web.dev/learn/pwa/os-integration/)
- Any browser upload page also receives files via the normal file picker; share-to-browser isn't a thing, so PWA install or an app is needed for share-sheet integration.
- **mDNS `.local` in Chrome works natively since Android 13** (not backported ≤11; Private DNS can interfere). Show the IP as a fallback. [esper.io](https://www.esper.io/blog/android-dessert-bites-26-mdns-local-47912385), [androidpolice](https://www.androidpolice.com/android-mdns-local-hostname/)
- **Web Bluetooth is available on Android Chrome** ([caniuse](https://caniuse.com/web-bluetooth)).
- **Local network permission**: Android 16 opt-in (`NEARBY_WIFI_DEVICES`), Android 17 mandatory `ACCESS_LOCAL_NETWORK` for targetSDK 37 — browsers included. iOS has had the per-app prompt since 14. [Android docs](https://developer.android.com/privacy-and-security/local-network-permission)

## 4. Device-side patterns on ESP32-C3

- **Onboarding**: SoftAP + captive portal to collect home-Wi-Fi credentials (STA is nicer for daily use: phone keeps internet, `.local` name works); keep hotspot as a fallback for travel. Show a `WIFI:T:nopass;S:<ssid>;;` (or WPA) QR — iOS 11+/Android cameras join natively — then a second QR with the URL. [WiFi QR format](https://wifiqrcode.app/guides/qr-code-format-technical), [Apple forums](https://developer.apple.com/forums/thread/97060), [Kreuzer captive-portal provisioning](https://www.haraldkreuzer.net/en/news/esp32-wifi-provisioning-soft-ap-and-captive-portal)
- **Throughput ceiling**: C3 iperf TCP ≈ 20–22 Mbit/s on ESP-IDF, ~7 Mbit/s with Arduino stack; SD over 1-bit SPI writes ~1 MB/s (≥512 B blocks; tiny writes drop to ~0.4 MB/s). Net expectation: **300 KB/s–1 MB/s** for a well-implemented upload; CrossPoint's 4 KB HTTP buffer and reports of KB-sized files taking minutes show it's easy to do badly. [tutoduino](https://tutoduino.fr/en/esp32-wifi-performance/), [esp-idf #10022](https://github.com/espressif/esp-idf/issues/10022), [SD benchmarks](https://github.com/drorgl/esp32-sd-card-benchmarks), [pschatzmann SD](https://www.pschatzmann.ch/home/2025/03/25/test/)
- **Streaming to SD**: ESP-IDF `file_serving` example streams `httpd_req_recv` into an 8 KB scratch buffer and `fwrite`s each chunk — no RAM buffering; raise its 200 KB `MAX_FILE_SIZE`. Prefer raw `PUT`/WebSocket binary (no multipart boundary parsing) with 16–64 KB SD writes. [file_server.c](https://github.com/espressif/esp-idf/blob/master/examples/protocols/http_server/file_serving/main/file_server.c)
- **Resumable**: accept `Content-Range`/offset on PUT (tus-style) so a dropped Wi-Fi link resumes; CrossPoint's `START:size` protocol lacks this.
- **WebDAV**: ESPWebDAV / s60sc implementations exist; mounts in Finder (⌘K `http://ip/webdav`), Explorer, Android file managers; not stock iOS Files. [ESPWebDAV](https://www.arduinolibraries.info/libraries/esp-web-dav), [s60sc webDav.cpp](https://github.com/s60sc/ESP32-IO_Extender/blob/main/webDav.cpp)
- **OPDS client** on-device pulls from Calibre-Web/Kavita/Komga/Gutenberg — no phone needed at all.
- **USB MSC impossible on C3**: it has only a fixed-function USB-Serial/JTAG controller; USB-OTG + TinyUSB MSC (SD as card reader) needs S2/S3. On an X3 the SD must be removed or Wi-Fi used. [ESP-IDF C3 USB-Serial-JTAG](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-guides/usb-serial-jtag-console.html), [ESP-FAQ USB](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/peripherals/usb.html), [S3 TinyUSB MSC](https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/usb_device.html)

## 5. Best-loved UX

BooxDrop is the reference: "nothing to install, no pairing, runs in any browser", scan QR or type URL, drag-and-drop, progress bar, done, two-way. KOReader/Calibre wireless is respected but fiddly (firewall, discovery fails when Wi-Fi sleeps, per-file library refresh slows bulk sends). Send-to-Kindle wins on the phone because the share sheet is one tap — but needs cloud and conversion. Xteink's stock app is "clunkier" and firmware-gated. Ideal: tap *Transfer* on the reader → screen shows Wi-Fi QR + URL QR → phone opens page instantly (captive portal or scan) → drop/pick files → per-file progress → "Done, 3 books added" on both screens.

## Recommended sideloading design for an ESP32-C3 e-reader

1. **Device-hosted web page (primary)** — `http://<name>.local` + IP, STA on home Wi-Fi with hotspot fallback; two QR codes on e-ink; streamed binary upload (WebSocket or raw PUT with `Content-Range` for resume, 16–64 KB SD writes) with multipart fallback; ESP-IDF stack for ~20 Mbit/s. *iOS:* Safari file picker from Files (Books → Save to Files first); captive portal only shows a link to open Safari. *Android:* same page installable as PWA with `share_target` → native share-sheet target.
2. **iOS Shortcut "Send to Reader"** — shipped as a downloadable Shortcut (share sheet → POST Form to `/upload`); the only no-app share-sheet path on iPhone.
3. **OPDS client** — saved servers (Calibre-Web/Kavita/Komga/Gutenberg/Standard Ebooks); zero phone involvement.
4. **Calibre wireless (smart device app)** — TCP 9090 + UDP 54982/48123/39001/44044/59678; for desktop Calibre users.
5. **WebDAV** on the same HTTP server — Finder/Explorer/Android mounting; not native iOS Files.
6. **BLE** — only for Wi-Fi provisioning/wake-up, never for books (30–80 KB/s ceiling, requires native app on iOS).
7. **Not viable**: USB MSC (no OTG on C3), AirDrop, email-to-device (needs cloud).
